# Product and architecture decisions

These decisions preserve the original handoff rather than replacing it. Status is **accepted direction** unless explicitly marked as an M1 implementation fact or optional evaluation. Implementation progress lives in [the roadmap](roadmap.md) and linked issues. The user's later instructions can revise a decision; record the reason and consequences here when that happens.

## D1 — Discovery is the product

The service should surface worthwhile ideas and developments outside followed sources, preserve history, and offer conversation through MCP plus a curated daily briefing. It is not a full-featured RSS reader or unread-count UI. Feed ingestion is a foundation, not the product's completion criterion. Basis: handoff §§1, 8, 9, 10, 12.

## D2 — One small self-hosted application

Use Bun, strict TypeScript, Hono, SQLite through `bun:sqlite`, Drizzle migrations, FTS5, the official MCP SDK, `Bun.cron` and Docker Compose with a persistent volume. M1 tested Bun 1.4.4 and exactly pinned dependencies. Domain rules stay independent of the runtime/provider, with small adapter boundaries. Exclude microservices, distributed queues, a separate DB service, mandatory local models, vector databases and agent frameworks. Basis: §§3, 14; observed M1 manifest, migrations and Compose configuration.

## D3 — Processing runs continuously, publication separately

Persist/index at ingestion, then independently extract, analyse, score and expose availability. Pending/failed AI must not hide collected items or stop other sources. Publication selects already processed content. Developing digest reads use completed scores; freezing captures an immutable prepared snapshot and is not evidence of delivery. Scheduling callbacks only wake durable SQLite jobs; they do not own recoverable state. Preserve retries, bounded work, leases and fencing. Basis: §§4, 11. Extraction and deterministic scoring handlers run independently of optional analysis; existing extracted items are queued by migration and remain searchable while processing is pending.

## D4 — Identity and attribution are independent

A canonical item can have many source-native references and parents. Email originals may lack a public URL and must remain searchable after their article links are expanded. Preserve original and resolved URLs where useful. Canonical URL cleanup must not erase meaningful parameters or merge broad-topic coverage. M1 handles exact URL identity and conservative digest fan-out; semantic/event grouping is future work. Basis: §§5, 6, 10.

## D5 — Interests and editorial rules are separate, versioned objects

Interests describe what matters to this user; editorial profiles describe how a content type is evaluated and presented. Priorities, positive/negative preferences, search queries, expiry, criteria, model provenance and explicit feedback need persistent versioning. Unread or missing clicks must never become negative feedback. Samples are not real user preferences. Basis: §§6, 7.

## D6 — Deterministic decisions first, bounded optional AI

Use deterministic filtering, ranking, novelty, redundancy and curation wherever practical. Use OpenAI-compatible providers for structured analysis behind a small interface; optional specialist judgments must expose their provenance and failure fallback. Scoring records components, versioned profiles and uncertainty, and uses confirmed provider acceptance or reconciled sent state and the frozen edition snapshot for prior-presentation evidence. Grouping, source edits and a prepared edition do not establish prior delivery; unresolved outcomes remain uncertain. Provider acceptance does not establish readership. Conservative update comparisons use historical snapshot evidence and preserve earlier editions and scores. Offline regression reports preserve explicit label coverage and unknown cost; synthetic fixtures do not establish real-world quality. Do not build an internal conversational assistant. Embeddings require a measured retrieval gap after simpler FTS improvements have been evaluated. Basis: §§3, 6, 7, 9, 13, 14.

## D7 — Discovery is explicit, budgeted and auditable

Begin with bounded scheduled queries from active interests, persist query lineage/results/cost/yield, and reserve some capacity for adjacent interests and unexpected connections. Refine from explicit feedback, without an autonomous loop. Provider availability, terms, limits and cost must be validated when an adapter is implemented; the handoff's provider examples are candidates, not a claim all APIs exist. Basis: §§7, 8, 13.

## D8 — Private MCP is the first interface

Use official SDK Streamable HTTP and source-linked tools; stdio is optional. Read tools precede mutation tools. The connecting client reasons conversationally; service responses distinguish source claims, summaries, uncertainty and unavailable content. MCP/admin stay private and authenticated. Only an appropriately signature-verified incoming webhook becomes public. Consequential mutations need scoped confirmation. Basis: §§3, 5, 9, 11. M1 provides four read tools; the full tool list remains planned.

## D9 — Email originals and delivery have durable state

Resend is the initial inbound/outbound provider, isolated behind small interfaces so IMAP can follow later without changing domain logic. Verify and persist webhook events quickly, then retrieve/process asynchronously; reconcile received-email listings for missed events. Freeze immutable digest editions and durable send state before calling the provider. Use provider idempotency within its actual guarantees; an ambiguous send must be reconciled rather than retried automatically. Basis: §§5, 10, 11. Default publication is configurable 06:00 Europe/London, with persisted local edition identity and DST tests.

## D10 — History outlives disposable content

Separate raw/content retention from stable identity, provenance, grouping, feedback and publication metadata. Historical editions and ranking explanations must remain understandable after model/profile changes or content expiry. Defaults retain data until configured cleanup is explicitly introduced; operators choose documented retention policies. Backup/restore is a core operational feature. Restoring a pre-send snapshot requires provider reconciliation before re-enabling delivery. Basis: §§6, 9, 10, 11.

## D11 — HTTP/API first, browser only where justified and permitted

Prefer ordinary HTTP extraction and structured APIs for GitHub/HN. Reddit initially comes through search results, newsletter notifications and manual submissions; unavailable source content must be labeled honestly. An optional browser interface may support a permitted fallback, with concurrency/time/resource limits and failure isolation. Browser automation must never become core infrastructure or circumvent access restrictions. Basis: §5; M5 evaluates concrete browser implementation.

## D12 — Completion means evidence, not issue-count reduction

Use versioned recorded evaluation data, offline score replay, source-linked outputs and failure-injection tests. Measure relevant discoveries beyond subscriptions, top-result precision, duplicates, known-important-development misses, source reliability, cost/useful discovery and latency. Capture a comparable Newsweave baseline when practical and report when it is unavailable. Required issues need merged, verified behavior. M5 refinements and optional stdio require a documented evaluation and implemented adoption or justified non-adoption; optional ideas do not become mandatory features merely because they have tracking issues. Basis: §§12–15.

## D13 — Story groups are explainable and independent of item identity

A specific-development group is a _relationship_ among canonical items, not a replacement for any item or original source citation. Prefer deterministic, negative-tested lexical, entity, version, temporal and content-hash evidence to an unmeasured semantic model. Persist the rule version and explicit membership evidence. Corrections end memberships and retain their audit trail; a later substantive update is a distinct group with an optional directional historical link. Reconciliation runs through durable processing jobs and avoids paid analysis. Snapshot-wide calculation is the initial implementation, not an indefinitely accepted scalability guarantee. No vector store, mandatory model, external queue or publisher rewrite is justified by #6.

## Updating decisions

For a consequential change, record the affected D-number, evidence, chosen alternative, compatibility/data consequences and rollback. Update the affected issue and operator-facing README. Do not silently change the product toward reader UI, uncontrolled discovery spend or a provider-specific conversational system. The original handoff is an archived requirement source; new approved decisions are recorded here, not retroactively edited into it.

Inbound implementation: verified raw Resend webhooks commit message/event identities before acknowledgement; bounded background Receiving get/list requests use durable fenced leases and a paginated full rescan for overlap. Provider IDs remain distinct from RFC Message-ID. Bodies remain untrusted; attachments are not fetched. Retrieved newsletters become URL-optional, independently searchable original items; linked articles enter the shared ingestion pipeline with parent attribution and canonical deduplication. Filter newsletter chrome and tracking conservatively without fetching arbitrary redirect URLs. Missing bodies and unsupported attachments remain explicit limitations. A single service instance enforces the configured request cadence.

Cross-development historical comparisons use only directional, versioned group relations and immutable snapshots from provider-accepted or reconciled-sent editions. The comparison preserves edition, item/group, citations frozen in the edition snapshot, score snapshot, relationship evidence and bounded content comparison in score provenance. Candidate content must match its latest non-backfilled observation or a fenced extraction tied to that observation; current mutable source associations are not presented as frozen citations. Ended relationships and memberships remain visible as historical evidence but cannot produce a possible-follow-up classification. A relation can support a possible-follow-up label only when temporal and content provenance is coherent; it never establishes a verified update or duplicate, and uncertain evidence stays unknown. Relation changes fence and refresh scores on both groups. Provider acceptance remains distinct from readership.

### Outbound delivery and deferred acceptance

The #42 implementation requires operator reconciliation for an ambiguous send outcome immediately, including within Resend's documented idempotency retention window. The first possible attempt and immutable envelope are persisted before network work. An exclusive process lock and payload-bound confirmation protect reconciliation. Provider acceptance is not inbox delivery.

Required issue [#48](https://github.com/mhingston/newspulse/issues/48) adds append-only activity events and rebuilds missed editions from score provenance, observed content versions, and time-bounded story memberships as they existed at the scheduled publication instant. Already-frozen editions retain their existing path. Recovery is bounded to 31 due dates per wake-up, 500 candidates per date, and a 366-day activity ledger. Incomplete processing, resource limits, post-cutoff item merges, or an activity window crossing the migration/retention evidence boundary are recorded as unavailable instead of using later state. A changed timezone or publication clock records a configuration boundary and reanchors at the current local date rather than interpreting old cursor dates with new settings. The migration does not backfill historical activity: the prior table only retained the latest event, so a fully covered activity window becomes available after 24 hours. Confirmed delivery history remains separate from prepared editions. The required feedback links and mixed-edition link test remain assigned to [#18](https://github.com/mhingston/newspulse/issues/18); the HTTP boundary permits only the verified inbound webhook to be public.

### Explicit news discovery provider

The first search adapter uses [GDELT DOC 2.0](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/) for attributed news-index results. GDELT's [terms](https://www.gdeltproject.org/about.html) permit reuse of its released data with attribution; publisher content retains its own terms. Brave's [standard search terms](https://api-dashboard.search.brave.com/documentation/resources/terms-of-service) restrict persistence of results, making the standard offering unsuitable for the required provenance ledger without a separate storage license. GDELT provides neither general-web coverage nor documented offset pagination and does not supply article snippets in this mode. Unreported cost and publication time remain unknown. Both explicit and scheduled queries reserve durable bounded budget before calling the provider. Restore can rewind the local ledger, so operators must reconcile external usage before further discovery.

Every transport that dispatches discovery holds the same discovery process lock and enforces the restore guard. The CLI locks each explicit dispatch; the long-running service holds the lock for its full lifetime when scheduled discovery is enabled.

Scheduled discovery is opt-in and uses the existing durable discovery budget ledger. The planner reads only each interest's latest active version, excludes expired temporary interests, filters explicit negative terms from generated queries and candidate metadata, and deterministically allocates a configurable share of daily query slots to cross-interest term pairs. The daily share includes reserved manual provider requests. Query schedules retain all contributing interest IDs and versions; each run and result preserves that lineage. Explicit query and item-result judgments link through result, page and run records and refine future query order; no feedback is neutral and later item feedback replaces the prior judgment for that result. These records persist separately from editions and reading behavior. Each scheduled attempt advances its due time after a durable budget reservation but before provider work so a restart does not blindly repeat an ambiguous request. The existing discovery reconciliation remains the operator path for uncertain provider outcomes.

Profile query synchronization is amortized to once per minute and skipped while no daily budget or provider pacing capacity is available. Before dispatch, the chosen query is checked against current active interests, so profile edits and temporary-interest expiry take effect immediately; a mismatch also refreshes persisted schedule state. Recent execution deduplication uses schedule-key and start-time indexes with a configured-interval lookback; pre-key records use a bounded recent fallback. A restore-day pause suppresses only discovery ticks and produces no repeated scheduler errors; each tick rechecks the guard so discovery resumes after the UTC boundary.

### GitHub releases, activity and project discovery

Followed GitHub repositories use structured REST streams rather than page scraping: `releases` for published releases and `events` for finished issue/pull-request milestones only, deliberately excluding commits, stars and other unbounded activity. GitHub release and event IDs are the stable source-native identity; item identity follows the release URL so the same release observed through RSS and the API remains one canonical item with two source references. ETag and cursor state are persisted in `source_state`, conditional `304` responses continue from the cursor, repository renames follow documented redirects while identity stays stable, and a redirect to another stream or host fails closed. Rate-limit exhaustion yields a durable retry delay; authentication and permission failures fail only the affected source. HTML and release notes remain untrusted content.

GitHub has no documented official trending API. Discovery therefore uses the documented repository search API with explicit query signals (terms in description/readme, an activity window, and a star floor) as a reproducible, auditable approximation. Queries derive from versioned active interests, keep their contributing interest lineage, respect GitHub's 256-character query limit, and are recorded in the shared discovery ledger with `discovered` provenance distinct from followed sources. Budgets, restore gating and the discovery process lock are shared across providers; request pacing is provider-specific because GitHub's unauthenticated search quota is 10 requests per minute (about a six-second gap) while GDELT uses five seconds. `GITHUB_TOKEN` is optional, read from the environment at request time, and never persisted or logged; offline tests need no token.

### Hacker News submissions and discussion context

Followed Hacker News sources use the official read-only Firebase API rather than page scraping: one discussion item (`/item?id=ID`) or a public list feed (`/`, `/newest`, `/best`, `/ask`, `/show`, `/jobs`). The HN item ID is the stable source-native identity (`hn-item:ID`) and the discussion URL is the item's canonical identity. A linked article is inserted as a separate child item through the existing `item_sources.parent_item_id` relationship, so an article already known from RSS becomes one canonical item with both source references while the discussion remains separately retrievable. Text-only Ask HN posts need no external URL, and the `/jobs` list ingests `job` postings alongside stories. Extraction for a followed discussion reuses the stored structured body (`method: "structured"`) instead of scraping the HTML page, so the comment bounds cannot be bypassed. Deleted and dead stories/comments are recorded explicitly rather than dropped. Comment trees are bounded by depth, rendered count, requests, bytes and a poll deadline below the job lease; a bound hit is a partial success recorded as `truncated` and labelled in the text — including the request/byte/time bounds, so a large discussion does not fail and retry forever — while provider failures on the requested source still fail the poll. A discussion is re-ingested only when its structural fingerprint changes, with a periodic six-hour comment refresh for edits that leave the structure intact, and list feeds persist seen story IDs in `source_state.cursor` so restarts do not duplicate stories. Rate limits and 5xx responses yield a durable retry delay; a failing discussion fails only its own poll. HN titles, comments and text remain untrusted content.

Interest-driven HN discovery uses Algolia's documented search API with `hackernews` provider provenance in the shared discovery ledger. It shares budgets, restore gating, the process lock and a conservative five-second pacing gap with the other providers; followed discussions and negative interest terms are filtered. The linked article is preferred for extraction, with the discussion URL retained in the snippet for provenance.

### Manual submissions and Reddit identity

Manual, bookmark, notification-email and search-origin submissions share one intake service (`src/manual.ts`) instead of fetching user URLs in a transport handler. The caller supplies an idempotency key, the destination is validated without contacting it, and the submission plus its extraction job are committed in one short transaction so a stable canonical item ID exists before any network work. Origins share URL-based item identity with subscriptions and discovery: a page already known from RSS gains a `manual:<origin>` reference, and two submissions of the same URL resolve to one item. Manual sources are bookkeeping rows that are never polled and are excluded from subscription listings; `manual_submissions` is reported separately from discovery counts. Retrieval status is read back from recorded extraction evidence (`pending`, `extracted`, `unavailable` with reason and length), so an item never claims text it does not have.

Reddit discussions are identified by post ID rather than by host or slug. `reddit.com` (`www`, `old`, `m`, `np`), `/comments/<id>` and `redd.it/<id>` collapse to `https://www.reddit.com/comments/<postId>`, while the original URL, subreddit and post ID are retained in submission metadata. Because item identity follows `canonicalItemUrl`, a discovery search result, a digest-email link and a manual submission for the same discussion stay one item with multiple source references. Items ingested before post-ID identity are reconciled when a canonical submission arrives: the historical item is located by parsing the post ID out of any `url:` identity that matches it and merged into the surviving item, with its content, versions, jobs and `manual_submissions` provenance repointed before the duplicate is deleted, so a merge never leaves a dangling foreign key or loses submission history. Reddit content is only retrieved through the ordinary HTTP extraction path with its DNS/redirect/private-address checks: no browser, credential or undocumented API is used to bypass access restrictions, and a blocked page keeps its item, snippet and an explicit unavailable status. Retrieval status is read from recorded extraction evidence, including a terminal `failed` job, so an item never reports `pending` for work that has already failed. Search-origin submissions record the provider and run that discovered them, which is provenance only — the item is still a manual submission, not a discovery result.

### Authenticated mutations and scoped feedback

Six mutation tools (`add_source`, `remove_source`, `update_interest`, `submit_feedback`, `ingest_url`, `trigger_discovery`) share one application service (`src/mutations.ts`) with the CLI, so no transport re-implements source, profile, feedback or discovery rules. Every consequential change is a two-step preview/confirmation: the first call normalizes the request, computes a preview and a server-side payload hash, and returns a `confirmation_required` envelope with a `confirm_token`; the second call reconstructs the payload from the stored preview and applies it only if the hash matches. Confirmation tokens are single-use, expire after ten minutes and are bound to one action, so an unbound boolean, a replayed token or a token presented with different parameters can never authorize a change. Validation and consumption run in one short transaction with the effect, and no network work runs inside a transaction. `remove_source` disables future polling and cancels queued or running polls while retaining the source row, items, references and history; the cancellation clears the running lease, so an in-flight poll cannot commit late results. `trigger_discovery` re-checks the persisted daily budgets, reservations and provider pacing, so repeated or concurrent confirmations cannot exceed the ceiling.

Explicit feedback is recorded in `item_feedback` with item, optional edition/digest, source (`mcp` or `email`) and timestamp, and it re-derives the item's scores. When the item has a discovery result, the same signal is written to the existing `discovery_result_feedback` ledger so later query selection is refined with recorded provenance. Missing clicks, unread material and omitted items are never converted into events.

Digest feedback uses narrowly scoped, bearer-less links signed with a dedicated `FEEDBACK_SECRET` (at least 32 characters, distinct from `MCP_TOKEN`). A link token authorizes exactly one `useful`/`not_useful` action on one dated edition; only its SHA-256 hash is stored, it expires after 30 days, and replay is rejected. Tokens are derived deterministically from the edition/item/action/nonce, so re-rendering a retry sends the same links. The frozen digest row is never modified: delivery injects the links at send time through `FeedbackLinkDelivery`, and `GET /feedback/:token` only renders a confirmation form so link scanners and prefetchers cause no side effects; the explicit `POST` records the feedback. The feedback route is public because the token is the credential, but it cannot read data, mutate sources or profiles, or trigger spending. It joins the signature-verified `/webhooks/resend` route as the only public routes; `/mcp` and `/health` stay private and authenticated.
