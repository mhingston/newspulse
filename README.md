# Newspulse

A self-hosted foundation for a personal discovery engine. **M1 is implemented:** RSS/Atom → durable SQLite ingestion → authenticated, read-only MCP search. There is no feed-reader UI. Optional analysis, deterministic story grouping and an initial scoring pipeline are part of the developing M2 milestone. Optional daily email delivery and explicit, budgeted news discovery are available. Profile-driven discovery scheduling is opt-in.

## Run locally

Install **Bun 1.4.4 or later**. Tested dependencies are exactly pinned and locked.

```sh
bun install --frozen-lockfile
cp .env.example .env
# Replace MCP_TOKEN in .env with a random value:
bun -e 'console.log(crypto.randomUUID()+crypto.randomUUID())'
bun run cli init
bun run cli import-opml /path/to/miniflux.opml
# Alternatively:
bun run cli add-source https://bun.com/rss.xml 'Bun' 1800
bun run cli poll --force
bun run cli list-sources
# Use an ID from list-sources; settings are per feed.
bun run cli update-source SOURCE_ID 'title=New title' poll-seconds=3600 max-entries=500 max-bytes=5000000
bun run cli disable-source SOURCE_ID
bun run cli enable-source SOURCE_ID
bun run cli remove-source SOURCE_ID
# Re-importing an OPML never overwrites a title or interval; it reports already-subscribed feeds.
bun run cli search 'TypeScript'
bun start
```

The server polls on startup and continues throughout the day. Default polling is every 30 minutes, minimum 60 seconds. Configuration loads from `.env` through Bun. The example token is empty so a copied template fails closed. Supply a random token of at least 24 non-whitespace characters before starting the HTTP server. CLI commands operate locally and do not require the HTTP token.

## MCP

Connect a Streamable HTTP client to `http://127.0.0.1:3000/mcp` with header `Authorization: Bearer <MCP_TOKEN>`. The official TypeScript SDK client works directly:

```ts
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";
const client = new Client({ name: "personal-client", version: "1.0" });
await client.connect(
  new StreamableHTTPClientTransport(new URL("http://127.0.0.1:3000/mcp"), {
    requestInit: {
      headers: { Authorization: `Bearer ${process.env.MCP_TOKEN}` },
    },
  }),
);
const results = await client.callTool({
  name: "search_items",
  arguments: { query: "robotics", limit: 20 },
});
console.log(results);
await client.close();
```

Tools: `get_digest` (developing or frozen edition by `date`; `view: "list"` returns frozen edition metadata for `date`..`to`, newest first, never rebuilt from current scores), `explain_ranking` (recorded score history, source references and `exclusions` marking ineligible scores with their reasons), `get_story_group` (development ID and preserved article references), `search_items` (literal keywords, limit, offset, optional `source_id`, `since` and `until` in epoch milliseconds, `source_kind` one of `rss`, `github`, `hackernews`, `inbound`, `manual`, `discovery`, and `analysis_status` one of `pending`, `running`, `retryable`, `analysed`, `unavailable`, `failed`), `get_item` (ID, including `latest_score`), `get_submission` (manual/bookmark/email provenance and retrieved-vs-unavailable status), `get_feedback` (latest explicit per-item feedback), `get_sources` (`limit` default 50, max 100, and `offset`), `get_status`, `get_interests` (active interest profiles), `get_discoveries` (items found outside subscriptions, keyset-paged with `next_before`). Six mutation tools — `add_source`, `remove_source`, `update_interest`, `submit_feedback`, `ingest_url` and `trigger_discovery` — are described below. Search combines terms with AND. Results include canonical item URLs; `get_item` also returns all original resolved source references, including fragments and tracking context. Items without public URLs remain retrievable using their item ID and source-native reference. Source text is untrusted; model summaries and scores are estimates.

Transport is stateless Streamable HTTP with JSON responses. Stdio is optional in the handoff and not implemented. A client with a browser Origin must appear in `ALLOWED_ORIGINS`; the exception is the feedback form POST, which is accepted from the configured `FEEDBACK_BASE_URL` origin so an emailed link works without widening the MCP origin policy. Hosts must appear in `ALLOWED_HOSTS`; use hostnames without ports. No CORS policy is exposed for browser apps yet.

Every mutation tool is a two-step preview/confirmation flow shared with the CLI. Call it with its normal arguments to receive `status: "confirmation_required"`, a human-readable `effect`, and a `confirm_token`; call it again with the same arguments plus `confirm_token` to apply the change. The token is single-use, expires after ten minutes, and is bound to the exact previewed payload, so it cannot authorize a changed request, a different action, or a replay. `add_source` restores a previously removed source or creates a new one; `remove_source` disables future polling and cancels queued or running polls while keeping the source row, its items, references and history; `update_interest` appends an immutable interest-profile version and re-derives scores; `submit_feedback` records explicit `useful`/`not_useful` feedback (optionally tied to a delivered edition); `ingest_url` is an idempotent manual submission that queues extraction without fetching the destination first; and `trigger_discovery` runs one bounded query that still re-checks the persisted daily budgets, reservations and provider pacing. Removing a source fences any in-flight poll so it cannot commit late results.

## Docker Compose

```sh
# Set MCP_TOKEN in .env first.
docker compose up --build -d
docker compose exec newspulse bun src/cli.ts add-source https://bun.com/rss.xml Bun
docker compose exec newspulse bun src/cli.ts status
docker compose logs -f newspulse
```

Compose mounts a named persistent volume and publishes only on host loopback. The process runs as the image's `bun` user. Keep MCP and health endpoints on a private network or behind an authenticated private tunnel. When incoming email is enabled, expose only the signature-verified POST webhook through a TLS reverse proxy. Do not publish port 3000 on a public interface. For a private domain, add its hostname to `ALLOWED_HOSTS`, use TLS and retain bearer authentication. Anyone controlling CLI subscriptions can direct outbound HTTP requests; only import trusted subscription lists. Feed bodies and link text cannot alter source configuration.

## Operations

```sh
bun run cli status
bun run cli export-opml > subscriptions.opml
bun run cli poll             # Due sources and queued retries
bun run cli poll --force     # Schedule all sources; does not bypass active retries
bun run cli backup ./backups/newspulse-2026-11-08.sqlite
# Stop the service. Restore to a NEW path, then validate before switching DB_PATH.
DB_PATH=./data/restored.sqlite bun run cli restore ./backups/newspulse-2026-11-08.sqlite
DB_PATH=./data/restored.sqlite bun run cli status
DB_PATH=./data/restored.sqlite bun run cli search robotics
```

Backup destinations must not already exist. `backup` verifies its own output (integrity, foreign keys, search index, migration journal and table presence). The search index is checked row-by-row: every item must have exactly one index row with the same rowid, and indexed title and text must match the current content, extraction and summary. The migration journal must be non-empty and match a supported version prefix of the bundled migrations; `retention_purges` is required only for snapshots that include migration `0047`, so prior-version snapshots verify and restore without modification and removes a failed snapshot. `verify-backup FILE` runs the same check on any snapshot without modifying it and exits non-zero on failure. `restore` verifies the backup before copying and verifies the restored copy afterwards; a restored copy that fails verification is deleted, and its delivery and discovery guards remain in place. Back up regularly and copy snapshots off-host; raw live database-file copies can omit WAL data. Treat backups as private content. In Compose, create snapshots under `/app/data/backups` and use `docker compose cp` to export them. Stop Compose before restoring into a new file in its volume, then configure the container's DB_PATH to that file. Never overwrite a running database or its WAL/SHM sidecars.

Restoring an older snapshot can rewind provider-side state the local database no longer remembers. Before re-enabling delivery or discovery after a restore, audit provider activity since the snapshot as described in the delivery and discovery sections. A snapshot taken before a send requires provider reconciliation before delivery is re-enabled, even though the restore reports success.

Restore rehearsal (run before relying on a backup): take a snapshot with `backup`, `verify-backup` it, `restore` it into a new unused `DB_PATH` while the service is stopped, then run `verify-backup` and `status` against the restored copy. Confirm the integrity, foreign-key and search checks pass and that item counts match the snapshot. Before starting the service on the restored copy, confirm the delivery and discovery restore guards (`delivery-restore-preview`, `discovery-restore` steps in the delivery and discovery sections) and reconcile provider state for any send recorded after the snapshot. Restarting the service on the restored copy must not re-ingest or re-publish items already present. The automated rehearsal is `tests/restore-rehearsal.test.ts`, which builds a populated backup by driving the real pipeline (poll ingestion, processing stages with faked provider results, edition freeze and delivery preparation), restores it through the CLI and asserts integrity, foreign keys, FTS, idempotent re-polling, delivery restore guards and suppression of the restored outbox row.

Rollback after an upgrade: stop the service, restore the pre-upgrade snapshot into a new, unused DB_PATH, run `verify-backup` or `status` against it, and only then switch configuration. Do not run an older binary against an upgraded database in place.

### Derived content retention

Retention is disabled by default; all data is kept until an operator sets a window. Two classes of disposable derived content can be expired:

| Variable                           | Removes                                                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `RETENTION_EXTRACTED_PAYLOAD_DAYS` | Extracted article text stored in the current extraction job result, once its generation is at least this old                         |
| `RETENTION_ANALYSIS_SUMMARY_DAYS`  | Model-generated analysis payloads for the current generation                                                                         |
| `RETENTION_FEED_TEXT_DAYS`         | Feed/extracted text (`content`, `content_versions`) for items whose latest observation is at least this old, once settled and scored |

Preview then apply, using the same window configuration:

```sh
RETENTION_EXTRACTED_PAYLOAD_DAYS=90 bun run cli retention-preview   # dry run; reports eligible, purged, deferred counts
RETENTION_INBOUND_BODY_DAYS=30 bun run cli retention-apply          # indexed, complete, unleased inbound email bodies only
RETENTION_EXTRACTED_PAYLOAD_DAYS=90 bun run cli retention-apply     # bounded batch (RETENTION_BATCH, default 500)
```

Feed text (`RETENTION_FEED_TEXT_DAYS`) is cleared and each row is marked with `purged_at`. Identity, source references, observation timestamps, story history, feedback and frozen digest bytes are kept. Purged text is reported as unavailable, is never treated as a blank body, does not trigger re-extraction, and is excluded from observed-update and delivery-history comparisons. Items with a pending extract, group, analyse or score job are skipped. Before a purge clears a version's text it records a fingerprint — the SHA-256 of that version's original body, kept in `content_versions.text_fingerprint` (migration `0050`) — so a later re-poll that delivers a changed body is detected and the new text is stored as a fresh, unpurged observation under the normal update rules, while an unchanged body stays tombstoned. Rows purged before fingerprints existed keep the conservative title/URL-only comparison. Before the text is destroyed, each purged version records a fingerprint (SHA-256 of its original body, migration `0050`), so a later re-poll that delivers a changed body is detected: the new text is stored as a fresh, unpurged observation, the tombstone lifts and extraction re-runs under the normal update rules, while an unchanged body stays tombstoned. Versions purged before fingerprints existed keep only title/URL comparison and stay conservatively unavailable.

Each pass runs one short SQLite write transaction with no network or model calls and is safe to repeat; the unbounded diagnostic counts run after the writer lock is released. Indexed inbound email bodies (`RETENTION_INBOUND_BODY_DAYS`) are replaced by the same kind of tombstone (`{"status":"purged","reason":"retention"}`) only after the message is complete, linked to an item and unleased; unindexed, leased, pending or retrying messages keep their body, and the indexer skips tombstones instead of reporting a normalization failure. Each item with a purged body gets one `inbound_body` audit row. A purged payload is replaced by an explicit tombstone (`{"status":"purged","reason":"retention"}` or `{"purged":true}`), so `get_item` reports content as removed rather than presenting empty text. A purged summary is removed from every copy: the analysis row, the completed analyse job result and the settled budget reservation result. Accounting (tokens, micros, status) is kept, and the reservation key is renamed so a later `analysis-reanalyse` performs a fresh, budgeted regeneration instead of reusing the tombstone. Scoring treats a purged summary as unavailable. Every purge is recorded in the durable `retention_purges` audit table, which cleanup never deletes. The search index for the item is rebuilt in the same transaction, so removed text is no longer searchable.

Retention never removes or alters canonical item identity, URL aliases and redirects, source references, story groups and memberships, scores, frozen digests, delivery state, discovery ledger rows, feedback or manual submission metadata. Content observations and feed text are retained as history: only each row's disposable text payload is cleared by `RETENTION_FEED_TEXT_DAYS` (identity, timestamps and the body fingerprint stay), and inbound email originals are the provenance record, so `RETENTION_INBOUND_BODY_DAYS` is the only window that replaces a stored original (with a tombstone).

A generation is skipped while any extract, analyse, group or score job for its item is pending or running, so in-flight work is never purged. Grouping reads extraction text to detect syndicated coverage, so it is included in this check; once grouping has settled, the established group memberships and their stored evidence are kept, so a later library-wide reconciliation does not re-plan them from the shorter feed snippet. While any analysis reservation is in the `reserved` state, which can represent an ambiguous provider outcome, summary purges are paused for the whole database until the reservation is reconciled. Any pending `analyse` job blocks payload purge for its item. When analysis is disabled, its job stays pending, so payloads for those items are kept; this is the conservative choice, and operators who want payload expiry without analysis should enable it only after reviewing `retention-preview` deferred counts.

Logs are JSON on stderr with source ID, outcome, item count, attempt and duration. `get_status` / `cli status` report source errors, poll queue totals and processing job counts grouped by stage and state. `get_status` / `cli status` also include a read-only `health` block: `ready` is false when any warning is present. Warnings are `expired_leases` (processing jobs whose lease has passed without renewal), `failing_sources` (at least 3 consecutive failures), `truncated_sources` (an enabled RSS/Atom feed whose latest poll exceeded its `max-entries` budget, so entries were omitted; listed in `health.truncated_sources` with its entry count and budget; Hacker News and GitHub truncation has other causes such as comment depth or request limits and is not reported by this warning), `ambiguous_deliveries` (an email send whose outcome is unknown and needs reconciliation, never automatic resend), `analysis_envelope_breach`, and `queue_age` (a pending processing stage whose oldest job is over one hour old, measured from when the job entered its queue position rather than its retry deadline; stages that are not enabled by configuration, such as `analyse` without `ANALYSIS_*`, are not warned about but remain in queue counts). Failing-source warnings consider only enabled, non-removed sources, and source titles and errors redact URLs to origin and path so feed tokens never appear. `analysis_cost.known_cost_micros` counts each provider request once: an identical reanalysis that reuses a prior result copies its cost without a new charge and is not summed again. `analysis_cost.unknown_cost_count` counts analyses whose provider cost was not recorded; it is reported separately and never summed as zero. The health block never changes state and never includes credentials, raw email bodies or untrusted source text. Thresholds are fixed defaults in `src/health.ts`; source polling concurrency and per-host fairness are configured with `POLL_CONCURRENCY` and `POLL_PER_HOST_CONCURRENCY`; extraction and scoring run with `EXTRACT_CONCURRENCY` and `SCORE_CONCURRENCY` ceilings, each stage slot is held until its handler settles so a timed-out handler keeps counting, and analysis and grouping stay singleton by design. `get_status` / CLI `status` also include a read-only `budgets` block: discovery usage for the current budget day (same rolling window the reserver uses) against the `DISCOVERY_DAILY_*` ceilings when they are configured (`limits` is null otherwise), and analysis lifetime tokens, micros, reservation count and envelope breach. It never changes state. `health.delivery_outcomes` counts deliveries by status (`pending`, `sending`, `sent`, `done`, `ambiguous`, `failed`), and `health.search_spend` reports lifetime discovery queries and reserved cost in micros. This is the reserved amount, not provider-reported spend, and it has no unknown-cost count; only `analysis_cost.unknown_cost_count` tracks unknown model cost. Counts are derived from durable table state on every read, so they survive restarts without double counting. Under load, stage concurrency stays within its ceilings and newly ingested items remain searchable while extraction is saturated; `tests/overload.test.ts` covers this. `get_item` reports processing attempts, retry deadlines and errors for each generation. Extraction and scoring run automatically; analysis is optional. HTTP `/health` requires the bearer token and returns `ok` (process liveness), `ready` and `warnings` from the same health report as `get_status`, plus `checked_at`. A supervisor should treat `ok` as liveness and `ready: false` as a degraded-but-running state that needs operator attention. Manual recovery: for `ambiguous_deliveries`, audit the provider's send history for that edition and reconcile the outbox row with `delivery-reconcile` (accepted or not sent); never resend automatically. For `failing_sources`, fix the feed or disable the source, then the poll resumes. For `queue_age` or `expired_leases`, confirm the worker is running; expired leases are reclaimed on the next claim. SQLite uses WAL, 5-second busy timeout and short transactions. Job leases expire after 60 seconds; retry backoff starts at 30 seconds, max five attempts per poll cycle. Reclaimed jobs and repeat polling are idempotent.

If a feed fails, inspect `last_error`, check its URL and network access, and allow the persisted retry. A terminally failed polling cycle is retried as a new cycle when that source is next due. No public endpoint changes subscriptions. Subscription operations are CLI-local: `update-source` accepts `title`, `poll-seconds`, `enabled=true|false`, `max-entries` and `max-bytes`; `disable-source` and `enable-source` are shorthand for `enabled`. `remove-source` is a soft removal: it prints how many queued or running polls it cancelled, while the source row, its items, references, content versions and frozen editions stay so citations keep resolving. A removed source cannot be edited with `update-source`. Re-importing its URL with `import-opml` or `add-source` restores the same source row, ID and history, and its prior title and interval are kept. A poll already running when a source is disabled or removed cannot commit, because its lease is cleared. Disabling and re-enabling does not revive a cancelled poll: the next poll is queued only when the source is due again or `poll --force` is used. Limitations: `import-opml` never overwrites an existing source's title or interval, and there is no bulk-edit command. Disabling or removing a source cancels pending polls and fences any in-flight poll; network work already started may finish, but its results cannot be committed. Removal hides the subscription and retains its source record, item references and history. Re-adding the same URL restores it; importing an already disabled feed leaves it disabled.

Feed limits default to 1,000 entries and 5,000,000 bytes per response; permitted ranges are 1–10,000 entries and 1–20,000,000 bytes. `get_status` and CLI `status` include the latest entry count and truncation flag, retained across a 304 response. A truncated feed may omit older entries and is reported by `truncated_sources` until a later complete poll clears it (or the source is disabled or removed); increase the budget where appropriate. Changing either feed budget clears validators, cancels any active poll and schedules a fresh fetch. Changing an interval schedules the next poll from the last successful poll or immediately if overdue. Original and resolved URLs remain in references. When a known source-native entry changes, its title and latest observed non-empty text become current and searchable; prior observed titles, bodies and source URLs remain in `get_item.content_versions`, and a new fenced extraction generation invalidates downstream work for that item. Frozen editions are not modified. Cross-source content observations are retained individually; this is not an assertion that one publisher's correction applies to another publisher's copy. Back up before upgrading; restore a pre-upgrade backup to a new stopped database path to roll back.

Content versions marked `backfilled` represent the item text present at upgrade time, copied for each existing source reference; earlier source-specific bodies were not retained and cannot be reconstructed.

## Validate

```sh
bun run typecheck
bun test
bun run smoke
```

The smoke test uses local RSS/Atom HTTP fixtures, imports OPML, ingests duplicate stories, reopens SQLite, verifies conditional requests, and searches/retrieves provenance using a real official MCP SDK client over HTTP. Tests never send email or make AI calls. Unit/integration tests cover retry deadlines, fenced lease reclamation, URL-less items, digest fan-out, backups, HTTP access controls, fail-closed template configuration and coordinated HTTP/worker shutdown. Feed regressions cover namespace-prefixed Atom, mixed XHTML text/links, out-of-line content summary fallback, escaped HTML URL attributes, original citations, publication-date enrichment and encoded byte streams.

Feed decoding follows [RFC 7303 §3.2](https://www.rfc-editor.org/rfc/rfc7303#section-3.2): BOM first, then HTTP charset, then XML declaration/autodetection, defaulting to UTF-8. UTF-16LE/BE and legacy encodings supported by Bun's TextDecoder are covered; unsupported encodings (including UTF-32) and invalid bytes produce explicit feed-health errors instead of silent replacement characters.

See [architecture and roadmap](docs/architecture.md) for the initial schema, reference-project findings, compatibility evidence, defaults and limitations. Semantic deduplication and proactive discoveries are not available yet. A synthetic offline regression baseline is available; it is not a measured real-world relevance-quality baseline. See [offline evaluation](docs/evaluation.md) for replay, comparison and limitations.

### Interest and editorial profiles

Profiles are explicitly configured; no example interests are activated automatically.
Create a JSON array such as the following, then import it using `bun run cli import-profiles profiles.json`. Edit the file with the same ID and incremented version to update it; versions are immutable and consecutive. `bun run cli list-profiles` lists all versions and `bun run cli export-profiles > profiles.json` exports their full history. Imports are transactional and reject unknown fields, including credentials. Back up the database before upgrading or changing configuration.

```json
[
  {
    "kind": "interest",
    "id": "example-robotics",
    "version": 1,
    "description": "Example only",
    "entities": ["robots"],
    "keywords": ["robotics"],
    "priority": 3,
    "positive": ["research"],
    "negative": ["advertising"],
    "queries": ["robotics research"],
    "lifetime": "persistent",
    "feedbackRefs": []
  },
  {
    "kind": "editorial",
    "id": "paper",
    "version": 1,
    "description": "Evaluate papers",
    "contentTypes": ["paper"],
    "criteria": [{ "dimension": "evidence", "weight": 1 }],
    "presentation": ["methods"]
  }
]
```

Priority ranges from 1 to 5. A temporary interest requires `expiresAt`, an epoch millisecond timestamp; at and after expiry it is excluded from active interests while historical versions remain available. Persistent interests omit `expiresAt`. Editorial criteria are separate from interests. Scheduled discovery is disabled by default; when enabled it uses each active interest's configured queries, records explicit query usefulness feedback, and reserves part of its query budget for bounded pairwise exploration across interests. `feedbackRefs` remains an explicit external reference and no discovery is scheduled by profile import alone.

Optional, deterministic starting editorial criteria for six content types are in `examples/editorial-profiles.json`; import them explicitly if useful. The scoring baseline applies recognized component weights when an analysis classification matches a profile; unknown dimensions are reported as uncertainty.
Article extraction runs asynchronously after ingestion for public HTTP(S) item URLs. Search and MCP retain feed text while full text is pending or unavailable. See [architecture notes](docs/architecture.md#http-article-extraction) for destination restrictions, limits and extraction behavior.

### Optional structured analysis

Analysis is disabled unless all six settings below are supplied. `ANALYSIS_ENDPOINT` is the complete HTTPS Chat Completions URL and must have no credentials, query or fragment. `ANALYSIS_KEY` is sent only in the authorization header; use a dedicated secret, not a profile. The selected provider must support non-streaming Chat Completions with `response_format: {"type":"json_object"}`, `max_completion_tokens`, and usage fields as described by the [OpenAI Chat API reference](https://developers.openai.com/api/reference/resources/chat). Compatibility varies: validate the selected provider and model before enabling it. [OpenAI structured output guidance](https://developers.openai.com/api/docs/guides/structured-outputs) describes limitations including refusal and incomplete responses; Newspulse validates output locally and rejects incomplete output. No provider requests run in default tests.

```sh
export ANALYSIS_ENDPOINT=https://api.openai.com/v1/chat/completions
export ANALYSIS_KEY='your-secret'
export ANALYSIS_MODEL='your-supported-model'
export ANALYSIS_TOTAL_TOKENS=180000
export ANALYSIS_TOTAL_MICROS=1000000
export ANALYSIS_CALL_MICROS=10000
```

Budget amounts are lifetime ledger ceilings, not daily limits. `ANALYSIS_CALL_MICROS` is an operator-supplied conservative upper bound in millionths of the billing currency for each request, including all provider fees; verify it against the chosen model's actual pricing and maximum request size. Each call permanently charges that full bound to the local cost ledger even when the provider reports no cost. The token reservation is 18,000 per request: 16,000 input bytes, 1,000 output tokens and 1,000 tokens of message overhead. This bound relies on the selected provider's tokenizer and request accounting fitting that envelope; a provider that can exceed it must not be enabled. The local ledger cannot prevent a provider from charging more than the operator's bound or reporting incorrect usage. Actual monetary cost is stored as unknown; consult provider billing. Exhaustion stops new requests. If reported token usage exceeds the reserved bound, the actual reported amount is recorded even if it exceeds the configured ceiling; this persists an envelope-breach flag and blocks later dispatch even when lifetime budget remains; it cannot reverse an already completed provider call. Inspect `analysis_envelope_breach` in status, stop the service, review the provider envelope and configuration, then run `bun run cli analysis-acknowledge-envelope` before restarting. No automatic budget reset exists.

Validated provider responses are persisted before the fenced job completes so a restart can replay them without another request. A received 429 or server error consumes its full reservation and may retry within the remaining budget. A fully received response that fails output validation retires its reservation while retaining its full charge; subsequent retries remain budgeted. A timeout or other ambiguous failure retains its full reservation and blocks further dispatch until an operator reconciles it. Stop the service and verify the provider's billing and request status first, then inspect `bun run cli analysis-reservations` and use `bun run cli analysis-reconcile KEY` to allow a retry. Reconciliation retains the full previous reservation as spent; a retry needs additional budget and may be chargeable. When analysis is enabled, the service holds an exclusive OS lock for the database until the process exits, including after shutdown starts; reconciliation refuses to run while the service holds it. This requires Linux with glibc and a local filesystem with working `flock` semantics; unsupported environments fail closed. Do not access the same database through hard links or delete its `.analysis.lock` sidecar while running. The OS releases the lock on process exit or crash. Never reconcile while a worker or provider request is still running. Job retry backoff and its five-attempt ceiling still apply. Once a failed job is reconciled or a budget is increased, run `bun run cli analysis-retry ITEM_ID` to explicitly requeue it. Back up the database before migration or reconciliation and restore only into a new stopped path.

Analyses preserve model, provider, prompt version, input hash, exact profile snapshots, claims, citations, uncertainty and reported token usage. Summaries are model-generated, source content is untrusted, and source claims are not verified facts. Missing extraction retains the feed text and source reference; items lacking usable text remain unavailable for analysis. To request reanalysis after an analysis completes, run `bun run cli analysis-reanalyse ITEM_ID`. Changed model or profile configuration creates a new version; identical input and configuration reuses an existing result. Publication and scoring remain separate.

### Story grouping (M2 issue #6)

A durable independent grouping stage groups coverage of **specific developments**, never broad topics. Canonical URL identity and historical aliases continue to control exact item deduplication. A story group preserves the individual articles and their original source URLs, processing generations, analyses and citations.

Evidence is deterministic: long, varied, identical source text identifies syndication; lexical event/action, product/version and temporal constraints identify same-event reporting. Membership records include the rule version, matched item, and evidence. Corrected observations close old memberships and retain them for audit. Later related events may have an explicit directional relationship but remain distinct groups. `get_item` reports current and historical grouping; `get_story_group` returns all current/historical members with original article details and related developments. `get_status` reports grouping counts.

Existing databases enqueue one backfill job when upgraded. Grouping jobs do not block ingested items from being searchable, and unchanged snapshots do not create new membership history or paid analysis work. Back up before migration, and if rollback is needed, restore that backup to a **new stopped database path** rather than downgrading an upgraded database in place. Future immutable newsletter editions will not be rewritten by regrouping.

**Limitations:** The initial rule is deliberately conservative and uncalibrated; some real shared events will remain distinct, especially if titles lack explicit event verbs or identifiers. Long identical boilerplate may be ambiguous. The initial snapshot-wide reconciler needs further scalability evaluation for large libraries and may require more focused invalidation later. No model, vector database or external queue is required.

### Initial scoring (M2 issue #7)

After extraction, a durable score job evaluates the item even when analysis is disabled or unavailable. `explain_ranking` returns saved runs, source references, component values, weights, eligibility, reasons, uncertainty and the input/profile/analysis provenance. Historical runs are retained; a historical score is not necessarily current. The explanation tool returns up to 20 runs by default (maximum 100); pass `next_before` as `before` to retrieve older runs. Search remains available during processing and is not ordered by these scores.

The deterministic baseline uses explicit active interests, lexical matches and preferences, publication age, text length and simple indicators for the other components. Matching editorial criteria adjust known component weights when an analysis classification is available. Components and totals range from 0 to 100; ties in the domain comparator use item ID. No interest is enabled by default, and missing clicks or unread state are not inputs. Citations and keyword indicators do not establish factual accuracy or source credibility. The optional specialist interface is disabled in the running service; its absence is recorded as uncertainty and requires no binary or provider.

Scoring is a development baseline, not a validated ranking. A conservative update rule compares successive non-backfilled observations of the same source-native item: a changed title and at least 20 new distinct body terms representing at least 20% of the current vocabulary raise novelty for seven days after observation. Incidental changes and other source references do not restart or erase that window. A lexical reversion to a retained comparison observation, or removal of more than half the new terms, cancels that source's evidence. The saved explanation includes the source, version IDs, new terms and rule version. This heuristic can miss meaningful updates and can mistake extensive unrelated changes for one; it does not verify claims. It does not infer that a user saw earlier coverage. Confirmed provider acceptance and reconciled sent state supply prior-presentation evidence from frozen edition snapshots; acceptance is not evidence that anyone read the email. Draft, failed and unresolved deliveries do not establish presentation. Missing or ambiguous evidence remains uncertain. Same-item updates are compared conservatively with the actual historical snapshot, and grouping alone cannot prove a meaningful follow-up. Directional relations between different story groups are compared under `related-delivery-v1` with the accepted edition's immutable item, citations frozen in that edition, score snapshot, relationship evidence and bounded content comparison retained in score provenance. The current candidate must match its latest non-backfilled observation or an extraction tied to that observation; current mutable source associations are not presented as frozen citations. Ended relationships and memberships remain visible but cannot produce a possible-follow-up classification. Cross-group comparisons remain advisory: even coherent post-acceptance evidence is labeled a possible follow-up, never treated as duplicate coverage or a verified update. Missing, stale, backfilled, contradictory or ambiguous evidence remains unknown. Relation changes invalidate and fence scores for both affected groups while preserving prior score rows and frozen editions. If a legacy or malformed frozen snapshot lacks the historical title, text or citations, the explanation reports unavailable evidence for those fields. History lookup is bounded to 100 matching edition items and 250 KB per frozen item snapshot. Synthetic offline evaluation does not establish real-world quality or cost per useful discovery.

Profile imports, completed extraction or analysis, grouping changes and delivery acceptance or reconciliation requeue affected scores; temporary-interest expiry, publication-age boundaries and expiry of an observed-update boost also trigger re-scoring. The score history remains available for comparison. Back up before upgrading: the migration adds score storage and queues existing extracted items. If rollback is needed, restore a pre-upgrade backup into a new stopped database path and verify it before switching. Inspect processing job counts and per-item stage status if scoring fails; ingestion and search do not wait for scoring.

### Offline scoring and grouping replay

Run `bun run cli evaluate tests/fixtures/evaluation-corpus-v1.json 5` to replay the synthetic corpus without a database, provider or email. The [evaluation guide](docs/evaluation.md) describes recorded results, configurable gates, comparison, missing labels and timing. Synthetic interests are examples, not the user’s profile.

### Developing and frozen digests

`get_digest` reads a developing draft or an immutable frozen edition by date. Drafts consider recent ingestion, source observations and first scoring of a content generation in the 24 hours ending at preview time, using completed current scores. The requested date must match the preview time in Europe/London. Pending grouping or scores return `processing`; terminal failures are explained as exclusions. The newest 500 candidates are considered, with truncation explicitly reported in the snapshot. A development with more than 20 source references or more than 4 KB of citation data, or a score snapshot over 200 KB, is excluded with a reason. The initial defaults are at most ten items, at most four per interest, and a minimum score of 50. No active interests can produce a `no_digest` result. Search and ingestion continue independently.

To prepare an edition locally, run `bun run cli digest-preview 2026-11-09` and inspect its decisions and rendered content. To freeze exactly that preview within five minutes, run `bun run cli digest-freeze 2026-11-09 AS_OF HASH`, using `confirmation.asOf` and `confirmation.hash` from the preview. Changed inputs, options or an expired confirmation require a new preview. A frozen date cannot be replaced; back up before upgrading and restore a pre-upgrade backup into a new stopped database path for rollback. Freezing prepares a snapshot and does not send email or establish delivery.

Summaries are labeled as model-generated and original source identities remain available even without a public URL. Each frozen decision includes selected items, score snapshots and feedback targets. Accepted delivery and reconciled sent state provide historical presentation evidence for later scoring, while a frozen draft alone does not. Historical catch-up defers when current score-validity state may have changed since the scheduled cutoff, or when a candidate already appears in an earlier frozen edition; it never rewrites that edition. A timezone or clock change records every unavailable local date in the missing range (up to 366 per change). Actionable scoped feedback links remain assigned to #18, and identifying outside-subscription discoveries belongs to later discovery work. Missing clicks are not feedback.

## Incoming email

Incoming Resend email is optional. Set both `RESEND_API_KEY` and `RESEND_WEBHOOK_SECRET` (or neither), configure a receiving domain or inbox in Resend, and register an `email.received` webhook at `https://YOUR-HOST/webhooks/resend`. Add that hostname to `ALLOWED_HOSTS`. Expose only this POST route through a TLS reverse proxy; keep `/mcp`, `/health`, and all other routes private. The supplied Compose port is loopback-only. The raw body is limited to 64 KiB, 10 seconds, and 16 concurrent requests per process and verified with the pinned Resend SDK and its Svix headers before event and message identities are committed. Duplicate events and messages are idempotent. The response does not wait for Resend retrieval.

A background worker retrieves message text and HTML, using bounded requests and fenced leases. It also scans the received-email list in pages, persists its cursor after each page, checks the newest page between historical pages, and restarts at the newest page after each complete scan to overlap previous scans. Transient and invalid responses retry after a minute with an error category; provider-reported missing messages are marked unavailable. Requests run sequentially from one service instance, at most one retrieval and one listing request per two-second wake-up; use a single running instance for this provider budget. List cycles wait 15 minutes after completion. A large inbox can take longer to scan; monitor the cursor and provider retention and quota. Listing is subject to Resend's account permissions and retention, so recovery cannot cover messages no longer available there.

The private SQLite tables `inbound_messages`, `inbound_events`, and `inbound_reconciliation` hold untrusted content and operational state; protect backups accordingly. Operators can inspect counts and `last_error` codes locally, for example `SELECT status, count(*) FROM inbound_messages GROUP BY status` and `SELECT available_at, attempts, last_error FROM inbound_reconciliation`. Errors are categories, not provider response bodies. Retrieved newsletters are indexed as independent, URL-optional original items. Eligible article links are ingested separately, deduplicated against other sources, and retain newsletter parent attribution. The original and its children can be searched before analysis completes; neither retrieval nor indexing sends a digest. Newsletter bodies and link text are untrusted data. Attachments are neither downloaded nor executed, and missing bodies cannot supply content or links. Received time remains separate from publication time; it is not invented as a publication date. `get_item` references include the newsletter sender, received time, provider/message identity, parent item and indexing diagnostics. Diagnostics indicate missing bodies, truncated links and unsupported attachments. Parsing bounds each body to 2,000,000 characters, scans at most 500 links and creates at most 50 unique child candidates. Link filtering is conservative and heuristic: it omits known opaque trackers and ad networks but cannot identify every advertisement or tracker. Known wrapper URLs are unwrapped locally without requesting the tracker; the original citation is retained and only the cleaned destination is submitted for extraction. Article destinations still use the extraction safety checks.

Before enabling, back up the database as above. For a live contract check, use a dedicated Resend test inbox/domain and key, configure a TLS webhook, send a non-sensitive test message, confirm the event and completed body in the private database and search for the original and eligible linked articles through MCP, then temporarily disable the webhook and confirm a second test message is found by list reconciliation. This is an operator-run check requiring configured credentials and DNS; automated tests use fixtures only. To roll back, stop the service and restore the pre-upgrade backup into a new path.

### Daily email delivery

Outbound delivery is opt-in. Set `DELIVERY_ENABLED=true`, `RESEND_API_KEY`, `DELIVERY_FROM` and `DELIVERY_TO`; the sender must be authorized on a verified Resend domain. `DELIVERY_TIMEZONE` defaults to `Europe/London` and `DELIVERY_TIME` to `06:00`. Use plain email addresses. Inbound webhooks additionally require `RESEND_WEBHOOK_SECRET`. An empty edition is recorded without sending. A frozen edition and its outbox entry commit before the network call, and retries reuse the same frozen message and idempotency key. Resend acceptance means acceptance by the provider, not inbox delivery.

Enabling delivery also requires `FEEDBACK_SECRET` (at least 32 characters and distinct from `MCP_TOKEN`) and `FEEDBACK_BASE_URL` (an HTTPS origin, no credentials or query). These sign the narrowly scoped, bearer-less feedback links appended to each delivered item. Each link carries a signed token that authorizes exactly one `useful`/`not_useful` action on one dated edition; only its hash is stored, it expires after 30 days, and replay is rejected. Links never expose `MCP_TOKEN`, cannot read data, cannot mutate sources or profiles, and cannot trigger spending. A `GET /feedback/:token` only renders a confirmation form — link scanners and prefetchers cause no side effects — and the explicit `POST` records the feedback. Feedback is stored separately from the frozen edition, which is never rewritten; explicit feedback re-derives scores and refines later discovery query selection, while missing clicks and unread material are never treated as feedback. Because `/feedback/:token` is bearer-less, it and the signature-verified `/webhooks/resend` route are the only public routes; keep `/mcp`, `/health` and everything else private behind the TLS reverse proxy.

Resend [retains idempotency keys for 24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys). Newspulse stops automatic retries when a send outcome is ambiguous and requires operator reconciliation; repeated claims are also bounded. Inspect `bun run cli delivery-list`. Stop the service and check provider records before reconciling an unknown outcome. Never assert `not_sent` without evidence; it permits another attempt. Check `bun run cli` usage for the reconciliation confirmation protocol. Keep system clocks synchronized and do not move them backwards. A restored backup can predate a send. The CLI restore creates a `.delivery-restore-pending` sidecar that blocks outbound startup; keep the service stopped, audit provider activity since the backup, reconcile matching outbox rows, and use `delivery-restore-preview` followed by `delivery-restore-confirm AS_OF HASH` only after every possible send is safely accounted for. A matching restored pending row can be reconciled as accepted with its provider ID. If an accepted edition has no outbox row but its sealed frozen edition exists in the restore, record it centrally for suppression with `delivery-suppress-preview EDITION_DATE RECIPIENT PROVIDER_ID` followed by `delivery-suppress-confirm EDITION_DATE RECIPIENT PROVIDER_ID AS_OF HASH`; the confirm is payload-bound and idempotent, so repeating the preview/confirm workflow with the same evidence commits once and a stale hash is refused. These commands cannot suppress a date without an existing sealed frozen edition. If an accepted edition is absent or cannot otherwise be safely suppressed, keep delivery disabled and do not confirm the restore guard. Copies made outside the CLI or moved without the sidecar bypass this guard and require the same manual audit before enabling delivery. The delivery lock requires Linux/glibc, a local filesystem with working `flock`, and an ordinary file database. Do not delete its lock file or access the database through hard links.

The scheduler catches up already-frozen missed editions and reconstructs eligible unfrozen missed editions from activity, scoring, content and grouping evidence that existed at each scheduled local publication instant. It processes at most 31 due dates per wake-up, in date order, and persists each frozen edition and unique recipient outbox before sending. A recovered edition is a preparation snapshot; only provider acceptance or operator reconciliation counts as delivery history. London clock changes use each date's scheduled instant.

Historical recovery is unavailable for a 24-hour activity window that begins before the `digest_history_state.evidence_from` timestamp written during upgrade: earlier installations retained only the latest activity time, so the old events cannot be reconstructed. The activity and score-validity ledgers retain at most 366 days. Historical curation requires a time-indexed score-valid event created after that evidence was introduced, and checks its recorded refresh deadline and all later invalidations through the scheduled cutoff; older score rows remain unavailable until rescored. Processing incomplete at the original deadline, bounded evidence limits, or an identity merge after that deadline also records an `unavailable` schedule-history row instead of using newer state. When an earlier frozen edition has an unresolved delivery for a candidate, the current date remains in retryable `processing` state until delivery completes or is reconciled. Reconciliation then excludes confirmed sends or permits retry after confirmed failure, without changing a frozen edition. A schedule timezone or clock change records a configuration boundary and reanchors the cursor on the current local date; dates from the old schedule are recorded as an unavailable range rather than rebuilt with the new clock. Inspect `publication_history` and `digest_history_evidence_from` in `bun run cli status` for these outcomes. A backup preserves the evidence ledger, while restoring an older backup can rewind it; use the delivery restore audit before enabling sends. Scoped feedback links remain owned by [#18](https://github.com/mhingston/newspulse/issues/18). Do not interpret a missing click as feedback. Back up before migration or enabling sending, and restore only to a new stopped path. Tests use fake providers and never send real email.

## Explicit and scheduled news discovery

The `discover` CLI performs a single explicit query against the [GDELT Project](https://www.gdeltproject.org/) DOC 2.0 news index. It does not schedule searches or subscribe to publishers. GDELT is a news index, not a complete web search; it supplies titles and links rather than verified article content or snippets. Its `seendate` is recorded as observation time, not publication time. Coverage and result ranking are controlled by GDELT and may be incomplete. Reaching the configured limit is recorded as potentially truncated; GDELT's documented API does not expose an offset cursor. An ambiguous empty JSON object is treated as an unavailable/invalid response, not proof that there are no matches. Search text and result metadata are untrusted. Normal extraction applies public-address and redirect validation to result URLs.

Before using discovery, back up the database. Set `DISCOVERY_DAILY_MICROS`, `DISCOVERY_RUN_MICROS`, and `DISCOVERY_QUERY_MICROS` to positive integers representing conservative per-day, per-run, and per-request upper cost bounds in millionths of your billing currency, then run `bun run cli discover 'your query'`. These local reservations are operator-supplied assumptions, not a provider price guarantee; actual cost is unknown, and the operator must verify applicable terms and fees. Query and result ceilings default to 10 queries and 250 results per UTC day and 1 query and 25 results per run; set `DISCOVERY_DAILY_QUERIES`, `DISCOVERY_DAILY_RESULTS`, `DISCOVERY_RUN_QUERIES`, and `DISCOVERY_RUN_RESULTS` to adjust them. Reservations are made atomically before requests and are never refunded on errors or empty results. Clocks must remain synchronized. Inspect `bun run cli discovery-runs`, `bun run cli discovery-pages`, and the private `discovery_results` table for reservations, timestamps, failures, provenance and outcome. GDELT requests are single-flight and at least five seconds apart after completion; `budget_exhausted` also covers this local pacing limit. A reserved page left by a crash has an unknown outcome and blocks GDELT requests. Stop any discovery processes, inspect the page, then use `bun run cli discovery-reconcile-preview PAGE_ID` and `bun run cli discovery-reconcile PAGE_ID AS_OF HASH` with its confirmation. This retires the page as outcome unknown, retains its full reservation, and does not retry it. If a run remains active after all its pages are settled, use `discovery-run-reconcile-preview RUN_ID` and `discovery-run-reconcile RUN_ID AS_OF HASH` to mark it interrupted without claiming that its query finished. A new query is subject to the remaining budget. Queries and results are private database content.

To enable profile-driven scheduling, set `DISCOVERY_SCHEDULE_ENABLED=true` plus the same budget values, then restart the service on Linux. `DISCOVERY_SCHEDULE_HOURS` defaults to 24 (allowed 1–168); `DISCOVERY_ADJACENT_PERCENT` defaults to 20 (allowed 0–75) of the daily discovery query budget, including manually dispatched queries, allocated proportionally across scheduler ticks. The service dispatches at most one scheduled query per tick to respect GDELT's request pacing. Profile query synchronization runs at most once per minute when budget and provider pacing allow; ticks with no dispatch capacity skip synchronization. A selected query is checked against current active interests immediately before dispatch, so expiry and preference edits take effect without waiting for the next full sync. The planner uses active profile queries first, then bounded combinations of terms from different interests. Explicit negative terms exclude matching queries and filter matching titles/snippets before ingestion. The scheduler runs outside the RSS/email pipeline and uses the shared discovery ledger; zero budget, restore guard, or provider failure does not stop subscribed-source processing. Restore-day pauses are quiet and discovery resumes automatically on the next UTC day. The service holds the discovery process lock while running, so a separate CLI `discover` command must wait until that service exits. Use `bun run cli discovery-plan EPOCH_MS` to preview deterministic queries, `bun run cli discovery-schedule` for persisted due times, last-run yield and feedback, `bun run cli discovery-feedback 'query text' useful|not-useful` to judge a query, and `bun run cli discovery-item-feedback ITEM_ID useful|not-useful` to judge the latest discovery result for an item. These actions record explicit operator feedback; no feedback leaves utility unchanged. Scheduled queries become due again after the configured interval; an attempt is deferred across restart before dispatch, and ambiguous provider work remains subject to the same reconciliation procedures above.

The subscription snapshot consists of RSS sources enabled when the run starts. Classification reflects existing item references to those sources at that point; an unknown item is a discovery candidate, not a claim that the publisher is unfamiliar or that the result is relevant. Duplicate URLs retain their per-query observations while sharing canonical item identity. A backup can predate external requests and their charges. Managed restores create a persistent sidecar that blocks discovery through the restore UTC date; stop all other instances, inspect provider activity, and adjust budgets before running discovery again. Copies made outside the CLI or moved without the sidecar bypass this guard and require the same audit. The lock requires Linux/glibc and a local filesystem with working flock; do not delete the lock file or use hard links. Stop the service and restore a pre-upgrade backup into a new database path to roll back.

### Followed GitHub repositories

Add a followed repository stream with `bun run cli add-source https://github.com/OWNER/REPO/releases` or `.../events`. The `releases` stream polls published releases, using GitHub's stable release IDs; edits become new observations and deleted releases are recorded explicitly once both cursors fully enumerate the list. The `events` stream polls a bounded activity scope — finished issue and pull-request milestones — rather than unbounded commit noise. Requests use ETag/conditional requests; a `304` continues from the stored cursor without re-ingesting. Repository renames are followed through GitHub's redirects while item identity stays stable by release/event ID, and a redirect to an unrelated stream or host fails closed. Rate-limit exhaustion schedules a durable retry delay instead of retrying in a tight loop, and authentication/permission failures fail only that source's poll. Atom/RSS release feeds such as `/releases.atom` remain plain RSS sources.

A release seen through the GitHub API and through an RSS feed for the same release URL shares one canonical item and keeps both source references, like newsletter attribution. GitHub token use is optional: set `GITHUB_TOKEN` to raise API rate limits. The token is read from the environment at request time and is never stored in items, cursors, diagnostics or logs, and no token is required for offline tests. Repository titles and release notes are untrusted source data and are only ever stored as content, never as instructions.

### GitHub project discovery

Set `GITHUB_DISCOVERY_ENABLED=true` to schedule bounded repository search from active interests. `GITHUB_DISCOVERY_HOURS` defaults to 24 (allowed 1–168) and `GITHUB_DISCOVERY_WINDOW_DAYS` defaults to 90 (allowed 1–365). The planner builds one deterministic, star-floored, time-windowed query per interest (for example `rust compilers in:description,readme pushed:>2025-12-01 stars:>10`), merges identical queries while retaining interest lineage, and degrades over-long term lists under GitHub's 256-character query limit. GitHub has no documented official trending API; a starred, recently active repository search is a reproducible approximation of relevance, not a trending guarantee. Results enter the shared discovery pipeline as "discovered" provenance distinct from followed sources, with the query and signal recorded in the existing discovery ledger and budgets. GitHub search shares the same restore guard and process lock; its unauthenticated search quota is 10 requests per minute, so the provider-specific pacing gap is about six seconds rather than GDELT's five. Use `bun run cli discover-github 'query'` for an explicit query and `bun run cli github-discovery-plan EPOCH_MS` to preview scheduled queries. Search results are private database content.

### Manually submitted URLs and Reddit discussions

Submit a URL with `bun run cli ingest-url URL [manual|bookmark|email|search] [SUBMISSION_ID]`. The command validates the destination, records the submission durably, and prints the stable canonical item ID immediately; content fetching, cleaning and analysis continue in the normal extraction pipeline, so a slow or blocked page never delays the caller. Reusing a `SUBMISSION_ID` is idempotent and returns the same item even if the URL spelling changes. A URL already present from RSS or another submission resolves to the existing canonical item and adds a `manual:<origin>` source reference instead of creating a duplicate. Submissions are counted separately in `bun run cli status` (`manual_submissions`) and never inflate discovery metrics; manual sources are intake bookkeeping and are not polled as subscriptions.

Validation rejects non-HTTP(S) schemes, embedded credentials, IP-literal hosts and `localhost`/`.local`/`.internal` names before anything is stored. Extraction still re-validates DNS, redirects and private address ranges at fetch time; a rejected or blocked page becomes an item whose recorded extraction status is `unavailable` with a reason, never fabricated text. Reddit discussion URLs (`reddit.com/r/<sub>/comments/<id>`, `old.`/`m.`/`np.` hosts, `/comments/<id>`, and `redd.it/<id>`) share one identity keyed by post ID, so a search result, a notification email and a manual submission resolve to one item; the subreddit, post ID and original URL stay in the submission metadata. Items ingested before post-ID identity are reconciled on the next submission: a historical item whose identity was the full old host/slug URL is merged into the canonical item (preserving its body and provenance) instead of creating a duplicate. Reddit content is retrieved only when extraction can reach it through ordinary HTTP — no browser, credentials or undocumented API is used to bypass restrictions, and blocked posts keep their snippet-level provenance with an honest unavailable status.

Inspect provenance with `bun run cli submission ITEM_ID` or the read-only MCP tool `get_submission`, which reports origin, submitted URL, snippet, Reddit subreddit/post ID, discovery provenance and the recorded retrieval status (`pending`, `extracted`, `unavailable` or `failed`) with its reason and text length. When one item has several submissions, `get_submission` returns all of them, earliest first, so no provenance is hidden.

### Followed Hacker News discussions and lists

Add a followed source with `bun run cli add-source 'https://news.ycombinator.com/item?id=ID'` for one discussion, or a list feed such as `https://news.ycombinator.com/` (top), `/newest`, `/best`, `/ask`, `/show` or `/jobs`. Ingestion uses the official read-only Firebase API (`hacker-news.firebaseio.com/v0`); no API key or browser is involved. The discussion item keeps the HN item ID in its stable native ID (`hn-item:ID`), its discussion URL as canonical identity, the submitter, score, comment count and submission time. A linked article is a separate child item, so a URL that an RSS feed also reports becomes one canonical article with both source references rather than a duplicate — the discussion stays its own retrievable item and the HN source reference records its parent discussion.

Link posts and text-only Ask HN posts both work; an item without an external URL simply has no article child. Deleted and dead stories/comments are recorded explicitly (`[deleted]`, `[dead]`) instead of being dropped. Comment trees are marked with indentation and bounded by depth (4), rendered comments (100), requests per poll (80), byte budget and a 45-second poll deadline below the 60-second job lease; each individual comment is capped at 2,000 characters, and when any bound or cap is hit the source records `truncated` and the text is labelled `[discussion truncated by ingestion bounds]`. A discussion is only re-ingested when its structural fingerprint (title, text, score, comment count, reply IDs) changes, so an idle discussion costs one request; a full comment refresh runs at least every six hours to catch edits that leave the structure intact. A request, byte, time or text-length bound stops the walk and keeps what was already collected as an explicitly truncated result; only a provider failure on the requested source fails the poll. `/jobs` list feeds ingest `job` postings as well as stories. List feeds remember recently seen story IDs in `source_state.cursor`, so a restart does not re-ingest the same stories; corrupt cursors fail closed. Rate limits and 5xx responses schedule a durable retry delay, and a failing discussion fails only its own poll — unrelated feeds keep polling.

Set `HN_DISCOVERY_ENABLED=true` to schedule one bounded Hacker News search from active interests each `HN_DISCOVERY_HOURS` (default 24, allowed 1–168). Queries come from versioned interests and are recorded in the shared discovery ledger with `hackernews` provider provenance, sharing budgets, restore gating, the process lock and a five-second provider pacing gap. Followed discussions and stories matching an interest's negative terms are skipped. Use `bun run cli discover-hn 'query'` for an explicit search and `bun run cli hn-discovery-plan EPOCH_MS` to preview queries. HN titles, comments and text are untrusted source content, never instructions.
